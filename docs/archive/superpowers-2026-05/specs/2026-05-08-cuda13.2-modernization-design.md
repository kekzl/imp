# CUDA 13.2 Modernization: `cudaMemcpyWithAttributesAsync` + Blackwell `add.f32x2`

**Date:** 2026-05-08
**Author:** Raphael Friedmann (kekz@kekz.org), brainstormed with Claude Code
**Status:** Spec — implementation plan pending

## Goal

Adopt two CUDA 13.2 / Blackwell features in the imp inference engine on the surface where they are clean drop-ins, no perf-driven restructuring. The work is a focused modernization, not an optimization push: it surfaces newer APIs at sites where they are physically meaningful, and explicitly documents where they are *not* applicable so the audit isn't repeated later.

## Non-goals

- No new wrapper / abstraction layer (`imp::cuda::memcpy_*` not introduced).
- No mechanical sweep of the other 142 `cudaMemcpyAsync` call sites.
- No restructuring of FMHA / SwiGLU / RMSNorm / `reduce.cu` to manufacture float2-paired operands for `add.f32x2`.
- No measurable perf delta is expected or required to merge.
- No change to the public C API in `include/imp/`.

## Background

CUDA 13.2 ships two features relevant here:

1. **`cudaMemcpyWithAttributesAsync(dst, src, n, attrs, stream)`** — extension of `cudaMemcpyAsync` that accepts a `cudaMemcpyAttributes { srcAccessOrder, srcLocHint, dstLocHint, flags }` struct. With zero-initialized attrs the semantics match plain `cudaMemcpyAsync`. Useful surface: NUMA placement hints for managed/host memory, and explicit `srcAccessOrder` (Stream / Relaxed / AnyStream) for stream-ordered host buffer reuse.
2. **Blackwell `add.f32x2` PTX** (`NV_PROVIDES_SM_100`, applies on sm_120) — vectorized FP32 addition, two lanes per instruction. Exposed in CUB ≥ 2.5 via `cub::SimdSum<float2>` in `cub/thread/thread_simd.cuh`. Falls back to two scalar `fadd` on pre-Blackwell targets via `NV_IF_ELSE_TARGET`.

Imp builds against CUDA 13.2 with `arch=compute_120a` (RTX 5090, GB202), so both features are available unconditionally on the build matrix.

### Why the surface is small

- imp's hot kernels (FMHA, GEMM, MoE routing, GDN scan) vectorize via `__half2` and tensor-core registers, not `float2`. The natural Blackwell SIMD knob for those paths is `mma.sync.kind::mxf4nvf4.block_scale`, not `add.f32x2`. See `memory/sm120_real_perf_levers_2026_05_04.md` for the broader perf-lever map.
- `cudaMemcpyAsync` covers most of imp's H2D / D2D traffic correctly; only paths where the *host* side is reused stream-ordered or where NUMA placement is non-trivial benefit from explicit attributes.

## Sites in scope

### M1 — `src/memory/layer_offload.cu:197`

H2D copy that streams an expert's raw weight bytes into an offload slot during MoE inference with weight offload enabled. Recurring per layer page-in, multi-MB per copy, on a dedicated `transfer_stream`.

Current:
```cpp
IMP_CUDA_CHECK_LOG(cudaMemcpyAsync(dst_base + e.offset_in_slot, e.host_ptr, e.raw_bytes,
                                   cudaMemcpyHostToDevice, slot.transfer_stream));
```

After:
```cpp
cudaMemcpyAttributes attrs{};
attrs.srcAccessOrder = cudaMemcpySrcAccessOrderStream;
attrs.srcLocHint     = { cudaMemLocationTypeHostNumaCurrent, 0 };
attrs.dstLocHint     = { cudaMemLocationTypeDevice, 0 };
attrs.flags          = 0;
IMP_CUDA_CHECK_LOG(cudaMemcpyWithAttributesAsync(dst_base + e.offset_in_slot, e.host_ptr,
                                                 e.raw_bytes, &attrs, slot.transfer_stream));
```

**Why these attribute values:**
- `srcAccessOrder = Stream`: the host pointer `e.host_ptr` is owned by the offload manager and is *not* mutated until the copy completes, so the stream-ordered re-use guarantee matches the existing contract. This is the documented default for plain `cudaMemcpyAsync` on pinned memory; the change is semantically null.
- `srcLocHint = HostNumaCurrent`: tells the driver that the source is on the CPU NUMA node closest to the calling thread. On WSL2 with one NUMA node this is a no-op; on multi-socket Linux hosts it allows the driver to pick the correct GPU<->NUMA path. No regression possible because it's a hint.
- `dstLocHint = Device, 0`: redundant since `dst_base` is a known device pointer, but keeps the attribute struct explicit for readers.

### M2 — `src/runtime/vision_pipeline.cpp:93`

H2D copy of pre-processed pixel tensor for vision inputs, fired per multimodal request.

Current:
```cpp
cudaMemcpyAsync(d_px, h_pixels, pixel_bytes, cudaMemcpyHostToDevice, stream);
```

After: same pattern as M1, with `attrs.srcAccessOrder = cudaMemcpySrcAccessOrderStream`. The host buffer `h_pixels` is owned by the vision preprocessing path and not reused until the copy lands.

**Why not also weight_upload.cu:** `weight_upload.cu:1037` and `:1812` are one-shot H2D paths run during model load, not on the inference hot loop. Modernizing them adds noise without leverage.

### F1 — `src/compute/gemv_dp4a_traits.cuh:722` and `:769`

Final partial-sum fold in the dp4a-traits-based GEMV kernels for Q-quantized weights. Both sites are NWARPS=4 reductions where the warp-leader thread folds `partial[0..3]` into a single FP16 output element.

Current (both sites are structurally identical):
```cpp
__shared__ float partial[NWARPS];
// ... per-warp warp-shuffle reduction lands its result in partial[warp_id]
__syncthreads();
if (threadIdx.x == 0)
    y_out[local_row] = __float2half(partial[0] + partial[1] + partial[2] + partial[3]);
```

After:
```cpp
#include <cub/thread/thread_simd.cuh>   // (if not already transitively included)
// ...
if (threadIdx.x == 0) {
    const float2 ab = make_float2(partial[0], partial[1]);
    const float2 cd = make_float2(partial[2], partial[3]);
    const float2 s  = cub::SimdSum<float2>{}(ab, cd);  // emits add.f32x2 on sm_120
    y_out[local_row] = __float2half(s.x + s.y);
}
```

**Why this is the only f32x2 site:** the gemv_dp4a final fold is the only location in imp where one thread holds four FP32 partials in registers ready to be reduced. Everywhere else either:
- Holds `__half2` lanes (FMHA softmax accumulator, SwiGLU, RMSNorm rescale) — fully vectorized via half-precision tensor-core paths.
- Reduces across threads via `__shfl_*_sync` — each thread holds a single float, f32x2 doesn't apply.
- Uses scalar FP32 across a loop body (`reduce.cu` rowsum, GDN scan) — would need a refactor to maintain two parallel accumulators, which violates the "no perf restructuring" non-goal.

This is a demonstrable application of the new PTX op rather than a perf-driven change. We do not expect a measurable end-to-end delta.

## Verification

### Build
- `make build` — must succeed against CUDA 13.2 toolchain inside the official Docker image.
- `cmake -B build && cmake --build build -j$(nproc)` — host build path must also succeed (tracks the host CUDA 13.2 toolkit).

### Tests
- `make test-gpu` — existing test suite covers all four sites (`tests/gemv_dp4a_*`, `tests/layer_offload_*`, `tests/vision_*`). No new tests required because the change is semantically null at neutral attribute values and the f32x2 fallback path is bit-exact with the prior scalar fold.
- `make verify-fast` — pre-merge regression gate (Q8_0 baselines + smoke prompt). Must pass with current 3% decode / 5% prefill thresholds.

### SASS sanity check (post-merge confirmation, not a gate)
```
cuobjdump --dump-sass build/src/libimp.so | grep -E "FADD\.X2|f32x2" | wc -l
```
Should return at least one match per gemv_dp4a kernel template instantiation. Zero matches means nvcc inlined the SimdSum back to scalar fadds — the swap is then harmless but should be noted in the PR description so the audit isn't claimed.

## Risks and mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| nvcc inlines `cub::SimdSum<float2>` back to scalar `fadd` | Medium | SASS check above. The change is semantically null either way; if PTX op doesn't fire, document it in the PR body and move on. |
| `HostNumaCurrent` is a no-op on WSL2 | High (expected) | Documented. Hint, not a directive — driver ignores cleanly. |
| `cub/thread/thread_simd.cuh` not transitively included from `gemv_dp4a_traits.cuh` | Low | Add the include explicitly; CUB header is part of the bundled CCCL in CUDA 13.2. |
| `cudaMemcpyAttributes` struct layout / field names differ from header expectation | Very low | Field names sourced from `/usr/local/cuda/include/driver_types.h:2430` at spec time; reverify in plan step. |
| New CUDA 13.2 API not present in CI image | Very low | `make build` validates against the same image; CI uses CUDA 13.2 already. |

## Out-of-scope (explicitly recorded so we don't re-audit)

- **`reduce.cu` rowsum / mean kernels** — using f32x2 would require maintaining two parallel FP32 accumulators across the strided loop. That is a real perf restructuring, not a drop-in.
- **FMHA softmax accumulator (`attention_blackwell.cu`, `attention_fmha_mxfp4_sm120.cu`)** — accumulator is FP32 scalar per row; the dominant time is HMMA-pipe-bound, not FFMA-bound (see `sass_audit_120a_no_tcgen05_2026_05_04` memo).
- **GDN scan FP32 chains (`gdn.cu`, `ssm_scan_kernel.cu`)** — sequential recurrence per chunk; pairing two tokens through f32x2 changes scan semantics.
- **142 other `cudaMemcpyAsync` sites** — most are D2D inside the inference loop where attribute hints have no surface, or one-shot startup copies.
- **`weight_upload.cu`** — one-shot at startup; no recurring leverage.
