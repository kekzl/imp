# sm_120 kernel notes

Notes on what was optimized for `sm_120a` (RTX 5090, GB202 Blackwell consumer), what didn't move the needle, and what's still open. Engineering reference, not a feature list.

For the canonical clean-sheet spec of the optimal attention kernel — tiling, smem
budget, MMA precision, and the lever-status table (what is shipped vs refuted vs
silicon-bound) — see [`sm120_optimal_kernel.md`](sm120_optimal_kernel.md).

## Hardware

| Spec | Value |
|---|---|
| Compute capability | `sm_120a` |
| SMs | 170 |
| Tensor cores | 680 (5th gen) |
| L1 / shared memory per SM | 128 KB (configurable split) |
| L2 cache | 96 MB (no L3 — that's only on data-centre Blackwell B200/B300) |
| Memory bandwidth | 1,792 GB/s (32 GB GDDR7, 512-bit) |
| FP4 dense / sparse | 3,354 / 6,708 TOPS |
| FP8 dense / sparse | 1,677 / 3,354 TFLOPS |
| FP16 dense / sparse | 838 / 1,677 TFLOPS |

`sm_120` uses register-based `mma.sync`, **not** `tcgen05` / TMEM / WGMMA. Native MMA shapes:

| Precision | Shape |
|---|---|
| FP16 | `m16n8k16` |
| FP8 | `m16n8k32` |
| FP4 (block-scaled) | `m16n8k64` |

The `f` family-feature suffix (`compute_120f`) enables FP8 MMA `kind::f8f6f4` and TMA warp-specialized grouped GEMM tactics. CMake < 3.31 doesn't understand the suffix — the build pins it via raw `--generate-code=arch=compute_120f,code=sm_120` and disables `CMAKE_CUDA_ARCHITECTURES`.

## What moved the needle

| Change | Path | Measured |
|---|---|---|
| FP8 attention prefill (`m16n8k32` QK^T) | `attention_fmha_sm120.cu` | +3.3% pp4096 |
| L2 persistence for KV | `set_l2_persist_kv` | measurable above 4K ctx |
| Aggressive split-K flash decode | `attention_paged.cu` | no regression at `tg256` |
| 16-byte `cp.async` for HD=256 | attention split-K | halves instruction count |
| Fused 3-way bias + sandwich-norm | various | -3 launches per layer |

| MoE expert-offload auto-pick (PR #54) | `executor_moe.cu` | Qwen3-Coder-30B Q6_K 77 → 234 tok/s |

## Why batch=1 decode is memory-bound

For a typical layer at 2048 tokens, 8 heads, 128 dim, FP16:

```
KV cache load   = 2048 × 8 × 128 × 2 B  = 4 MB
At 1.8 TB/s     → 2.2 µs per layer

Score compute   = 32 FLOPs/token × 2048 = 65 k FLOPs
At 838 TFLOPS   → 0.08 µs per layer
```

Memory:compute ratio is ~28:1. Compute is free. As a consequence, several optimizations that look promising on paper produce no measurable decode win on this hardware:

- **FP8 decode scores** — compute is already idle.
- **Warp specialization** — all warps already stream KV at peak bandwidth.
- **TMA for paged KV** — `cp.async` already at near-peak.
- **Triple buffering** — already double-buffered, marginal at best.

What actually helps decode:

1. **Smaller KV cache** (INT4, NVFP4, MXFP4) — bandwidth reduction is bandwidth gained.
2. **GPU clock boost** — RTX 5090 boosts to ~2,445 MHz under load (max 3,090 MHz).
3. **Batch > 1** — multiple sequences share weight loads, raising arithmetic intensity. imp's current decode tuning targets bs=1; multi-request batching is open work.

## Open kernel work

Tracked in [`roadmap.md`](roadmap.md). Highest-leverage items:

- Q4_K_M dense prefill gap vs llama.cpp — custom tiled MMQ kernel needed (dp4a shipped in PR #436 for small M; high-M gap remains).
- `cublasLtMatmulGrouped` with NVFP4 + device-side shapes — zero grouped algos returned on sm_120 as of cuBLAS 13.4. Re-probe on each toolkit release.
- MoE host-offload + CUDA Graphs (Phase 5.1) — needs kernel-driven slot resolution via device-side lookup table. Deferred (2-4 weeks).
