# Qwen3.8-27B — measured inventory and remaining-work plan

Phase 0 of the "first-class Qwen3.8-27B" brief. Every number below is read off
the staged checkpoints and off runs against `imp:test` (built from `72c642db`,
2026-08-24), not from recollection or from `docs/MODELS.md`.

**The headline finding: the model is already served end to end.** It loads,
generates coherent text, answers about images, and speculates with its own MTP
head. The brief was written as a from-scratch port; it is not one. What follows
separates what already exists from the four gaps that are real.

- `q_proj [12288, 5120]` = 2 × 24 × 256 → `attn_output_gate`, Q output doubled.
- `o_proj [5120, 6144]` = 24 × 256 → the gate is consumed before `o_proj`.

  `mtp_head.h` documents, and it lives in the main shard index, not a sidecar.

## Measured baseline

All on a free card (`gpu-busy-check.sh` FREE, 1016 MiB / 1 %), model
`Qwen3.8-27B-NVFP4` (self-quantized, 20 GB on disk), `imp:test` @ `72c642db`.

### Throughput, `imp-cli --bench --bench-pp 512 --bench-reps 3`

| arm | pp512 tok/s | tg128 tok/s |
|---|---:|---:|
| A baseline (`--bench` pins spec off) | 7425.67 | 88.60 |
| B `--set speculative.hybrid=true` (n-gram drafter, 79-81 % accept) | 7546.90 | 104.01 |
| C B + `--mtp-spec-decode 2` (MTP loaded, 90.7-91.4 % accept) | **1251.53** | **125.10** |

MTP buys **+41.2 % decode over A** and costs **-83 % prefill**. Both bench arms
ran with an identical KV pool (28 blocks / 896 tokens) and identical prefill
config, so the prefill collapse is not a memory artefact. Cause not yet
isolated — flagged for Phase 5, not explained here.

**Trap, hit during this measurement:** `--bench` pins `speculative.hybrid=false`
(`tools/imp-cli/main.cpp:88-95`), and Qwen3.8 is a hybrid, so measuring MTP the
obvious way silently measures nothing. Worse, `--set speculative.mtp_k=2` does
**not** enable MTP under `imp-cli` at all: the loader reads
`args.mtp_spec_decode_k` (`main.cpp:210`), fed only by the `--mtp-spec-decode`
flag. The startup log tells the operator to use `--set speculative.mtp_k=2`,
which is right for the server and wrong for the CLI.

### The two per-token/per-sequence constants

**KV cache: 65536 B/token (64 KiB), FP16.**
16 attention layers × 4 kv heads × 256 head_dim × 2 tensors × 2 B. Confirmed by
`engine_init_resolver.cpp:785` (`kv=65536 B/tok`). FP8 KV halves it to 32 KiB.

**DeltaNet state: 151.5 MiB/sequence.** Per layer: `h` = 48 v-heads × 128 × 128
× 4 B (FP32) = 3072 KiB, `conv` = 10240 ch × 4 × 4 B = 160 KiB. × 48 GDN layers
= 155,136 KiB. Confirmed verbatim by `ssm_state.cu:66`.

### What fits in 32 GB

Weights (NVFP4) 17920 MiB + context 1680 + library 3900 + arena 1851 + SF cache
1526 + workspace 602 leaves **≈ 5100 MiB** for KV *and* recurrent state.

| batch | GDN state | KV left | context/seq | verdict |
|---:|---:|---:|---:|---|
| 1 | 151.5 MiB | 58080 tok | 58080 | measured, healthy |
| 5 (auto default) | 757.5 MiB | 48512 tok | ~9700 | measured, the real operating point |
| 24 | 3636.0 MiB | **1376 tok** | **~57** | measured, loads but is unusable |
| 32 | 4848 MiB | — | — | **measured: does not load** |

At batch 32 the pre-upload reserve rises to 12715 MiB (from 7335 at batch 1),
leaving 16026 MiB for 17920 MiB of weights: the upload aborts at layer 61 with
`Failed to upload w_down for layer 61`. The recurrent state, not the KV cache,
is what makes 32-way concurrency infeasible on this card at NVFP4.

Auto-selected `max_seq_len` is 97204 (`vram_cap`), below the model's 262144.

### Serving correctness

32 concurrent `/v1/completions`, greedy, 4 prompts × 8, against the default
batch-5 server: **9/32 byte-identical to the batch=1 reference, 23 mismatches**.

That is not state leakage, and the data says so: for 3 of the 4 prompts all 8
concurrent answers are **byte-identical to each other** (prompt 2 gives 2
variants, and the odd one out is exactly the one that ran alone). Sequences do
not see each other's state; the batch>1 arithmetic path simply differs from
batch=1. imp's forward is not bit-deterministic across batch shapes generally —
this is not a Qwen3.8 property.

## The four real gaps

### G1 — `reasoning_effort` is accepted and ignored (Phase 1)

The checkpoint's `chat_template.jinja:47-54` branches on `reasoning_effort`
(`xhigh` default, plus `medium`/`low`) and injects different
`reasoning_instructions`. imp implements the field only for gpt-oss/Harmony
(`tests/fixtures/gpt_oss_chat_template.jinja`); nothing reads it for Qwen.

Measured: `reasoning_effort: low` and `: xhigh` both yield **67 prompt_tokens**
and identical output. A working implementation must change the rendered prompt,
so `prompt_tokens` is the assertion.

Work: thread the field from the request through `ChatTemplate` into the Jinja
environment. `src/model/chat_template.cpp:93`, `src/model/jinja.cpp`,
`tools/imp-server/` request parsing. Golden test in `tests/refs/`.

### G2 — the FP8 checkpoint is a quantization source, not a loadable model (Phase 1)

`Qwen3.8-27B-FP8` uses a per-layer file layout (`layers-N.safetensors`, 51 KB
config) that `imp-quantize` reads (`tests/test_quantize_fp8_source.cpp`), but it
cannot be served: 25.87 GiB of weights against ~27 GiB of usable VRAM before KV,
and sm_120 has no FP8 GEMM, so there is no path that would be fast anyway.

Recommendation: **state this as a limitation, do not build it.** The brief asks
for "the FP8 checkpoint layout" under loading; loading it to then dequantize
everything to FP16 would need 51.75 GiB. `docs/LIMITATIONS.md` is the deliverable
here, not code.

### G3 — 32-way concurrency does not fit (Phase 3)

Quantified above. The lever is the 151.5 MiB/sequence recurrent state, and the
options, cheapest first:

1. **Admission control already exists** — the scheduler bounds concurrency
   (`vram_budget.cpp:534`). Serving 32 *clients* at batch 5 works today and is
   what the 24 s / 32-request run measured. If the brief's "32 concurrent"
   means throughput, this is already met.
2. **Recurrent-state paging.** `RecurrentSnapshotStore`
   (`engine_kv_cache_init.cpp:717`) already snapshots GDN state to a host-side
   budget for prefix caching. Extending it to evict *inactive* sequence slots
   would decouple slot count from batch size. This is the real fix and the
   largest piece of work in the whole plan.
3. **Smaller weights** (MXFP4 `lm_head`/`embed`) buy ~1 GiB = ~7 slots. Cheap,
   partial, and interacts with G4.

Never: FP16 recurrent state. `engine_init_resolver.cpp:450` records the shipped
bug that produced 37 % scan divergence, and the contract pins FP32.

### G4 — prefill CUDA-graph capture is off on this model (Phase 5)

```
gemm_nvfp4 dequant workspace: largest NVFP4 weight is 2425.00 MiB > 512 MiB cap
  — prefill graph capture disabled
```

2425 MiB is `lm_head` dequantized to FP16 (248320 × 5120 × 2 B = 2426.6 MiB).
One tensor's M>1 fallback size disables capture for the entire prefill path.
Fires on both bench arms, so it is unconditional for this checkpoint.

## What is genuinely absent, and honestly so

The brief's Phase 2 asks for logits parity against HF transformers (max abs diff
< 2e-2, top-5 order, 20 prompts at 4k/32k, plus a DeltaNet state-drift check at
32k). **No such test exists for this model, and I have not run one.** The
evidence that currently stands in for it is a teacher-forced perplexity of 4.62
on `ppl_corpus_45k.txt` (`docs/MODELS.md:55`) and coherent output. That is
weaker than the brief asks for and it is the one place where "first-class"
cannot be claimed from what is in the tree today.

Same for Phase 5's competitive table: no llama.cpp or vLLM numbers for this
model on this card exist in `docs/BENCHMARKS.md`.

## Phase 2 result — reference parity, measured

Harness built for this: `diagnostics.dump_final_logits_dir` (the post-soft-cap
LM logits as FP32 `.npy`, one file per forward pass) and
`diagnostics.dump_gdn_state_dir` (the recurrent state, plus a per-pass stats
line). Reference is `transformers 5.15.1`, which carries `qwen3_5` natively,
running the BF16 checkpoint on CPU (51.75 GiB in 74 GiB of host RAM).

### The acceptance criterion cannot be met, and not because of a defect

The brief asks for max abs logit diff < 2e-2 against HF **bf16, same weights**.
imp cannot hold this model's BF16 weights: 51.75 GiB against 32 GB of VRAM. What
imp serves is the NVFP4 quantization, so every comparison here is 4.5-bit
weights against 16-bit weights, and 2e-2 is below the quantization floor by
construction — not reachable by fixing anything.

Measured, 17 prompts (14 short, 3 × 5823 tokens), imp NVFP4 vs HF BF16:

| statistic | min | median | max |
|---|---:|---:|---:|
| max abs diff | 1.672 | 1.969 | 7.572 |
| mean abs diff | 0.248 | 0.283 | 1.060 |
| pearson r | 0.8256 | 0.9855 | 0.9904 |
| total variation (softmax) | 0.0080 | 0.1131 | 0.2793 |

top-1 token agrees on 14/17; top-5 as an exact ordering on 2/17; top-5 as a set
on 6/17. The reordering sits inside the quantization noise — on short01 imp has
`[264, 524]` at 14.733/14.691 where HF has them at 14.75/14.50, a 0.04 gap
against a 0.28 mean error.

### What settles that it is quantization and not a wrong implementation

Teacher-forced perplexity on `ppl_corpus_45k.txt`, identical token count
(13810 counted) under both:

| | mean NLL | PPL |
|---|---:|---:|
| HF transformers, BF16 | 1.4860 | **4.4194** |
| imp, NVFP4 | 1.5304 | **4.6202** |

**+4.54 %.** That is the price of 4-bit weights and nothing else: this repo's
own GGUF Q4_K_M path measured +8.4 % against a BF16 reference on the same kind
of comparison. A wrong `attn_output_gate`, a mis-sized partial RoPE or a broken
GDN scan does not land 4.5 % off — it lands orders of magnitude off, or
incoherent. The architecture is implemented correctly.

The honest limit of this evidence: it does not isolate imp's arithmetic from the
quantizer's. A BF16-vs-BF16 run would, and it needs either a card that fits
51.75 GiB or a smaller checkpoint of the same architecture.

### DeltaNet state after 46579 tokens

`ctx32k_1`, 46579 prompt tokens, 24 chunks of 2048 through the recurrent path,
48 GDN layers × 786432 FP32 elements each:

| | pass 0 (16 tok) | pass 2 (first full chunk) | pass 24 (last) |
|---|---:|---:|---:|
| RMS | 0.0257 | 0.0648 | 0.0728 |
| min | -10.69 | -49.52 | -44.92 |
| max | 30.37 | 36.74 | 112.2 |
| non-finite | 0 | 0 | 0 |

**0 non-finite values across all 26 passes.** RMS is flat from the first full
chunk onward (0.0625 to 0.0762 over 24 chunks, no trend); the max saturates
rather than growing without bound. The state does not drift, which is the
property `mamba_ssm_dtype: float32` exists to protect and the one a logits
comparison at the end of a long prefill cannot see.
