# sm_120 kernel notes

What was optimized for `sm_120a` (RTX 5090, GB202 Blackwell consumer), what did not move the needle, what is still open. Engineering reference, not a feature list.

Canonical clean-sheet spec of the optimal attention kernel (tiling, smem budget, MMA precision, lever-status table): [`sm120_optimal_kernel.md`](KERNELS.md).

## Hardware

| Spec | Value |
|---|---|
| Compute capability | `sm_120a` |
| SMs | 170 |
| Tensor cores | 680 (5th gen) |
| L1 / shared memory per SM | 128 KB (configurable split) |
| L2 cache | 96 MB (no L3 - that's only on data-centre Blackwell B200/B300) |
| Memory bandwidth | 1,792 GB/s (32 GB GDDR7, 512-bit) |
| FP4 dense / sparse | 3,354 / 6,708 TOPS |
| FP8 dense / sparse | 1,677 / 3,354 TFLOPS |
| FP16 dense / sparse | 838 / 1,677 TFLOPS |

`sm_120` uses register-based `mma.sync`, **not** `tcgen05` / TMEM / WGMMA. Native MMA shapes:

| Precision | Shape |
|---|---|
| FP16 | `m16n8k16` |
| FP8 | `m16n8k32` |
| FP4 (block-scaled) | `m16n8k64` |

The `f` family-feature suffix (`compute_120f`) enables FP8 MMA `kind::f8f6f4` and TMA warp-specialized grouped GEMM tactics. CMake < 3.31 does not understand the suffix; the build pins it via raw `--generate-code` and disables `CMAKE_CUDA_ARCHITECTURES`. Two images ship (`CMakeLists.txt:48-50`): `arch=compute_120a,code=sm_120a` (SASS) and `arch=compute_120f,code=compute_120f` (**PTX**, not SASS - this line said `code=sm_120` until #1543).

**What a GB203 (RTX 5080 / 5070 Ti) runs:** the `compute_120f` PTX, JIT-compiled by the driver at load. Not the `sm_120a` SASS: `a` is architecture-specific and does not load on another chip. That costs the TMA-WS grouped GEMM tactics, so the CUTLASS NVFP4 fast path is degraded there. Untested - no such card here (#1651).

**SKU coverage:** every consumer-Blackwell card is compute capability 12.0, so the `sm_120a` SASS runs on the whole family, including the China-market GB202 variants (RTX 5090D, RTX 5090D v2). Only the RTX 5090 (32 GB GDDR7, 1792 GB/s) is tested. The 5090D keeps the full 5090 memory system; the 5090D v2 cuts it to 24 GB on a 384-bit bus (~1344 GB/s, −25%): expect a smaller usable model set (32 GB sizing assumptions in `docs/MODELS.md` don't transfer) and roughly bandwidth-proportional decode, since decode is memory-bound. See issue #1052.

## Why batch=1 decode is memory-bound

Typical layer at 2048 tokens, 8 heads, 128 dim, FP16:

```
KV cache load   = 2048 × 8 × 128 × 2 B  = 4 MB
At 1.8 TB/s     → 2.2 µs per layer

Score compute   = 32 FLOPs/token × 2048 = 65 k FLOPs
At 838 TFLOPS   → 0.000078 µs per layer
```

Memory:compute ratio is ~28,000:1. Compute is free.

Both numbers were wrong until #1668: the quotient read `0.08 µs` (a factor of 1023 too large) and the ratio `~28:1` was derived from it. The conclusion does not change, but the figures were unusable for sizing. 838 TFLOPS is also the **f16-accumulate** rate; FP32 accumulate, which `KERNELS.md:20` names as attention's largest compute loss, runs at 1/4 of it (253 TFLOPS measured, `tools/roofline/config.json:10`). At that rate the compute side is 0.00026 µs and the ratio still ~8,600:1. Consequences - optimizations that produce no measurable decode win on this hardware:

- **FP8 decode scores**: compute is already idle.
- **Warp specialization**: all warps already stream KV at peak bandwidth.
- **TMA for paged KV**: `cp.async` already at near-peak.
- **Triple buffering**: already double-buffered, marginal at best.

What actually helps decode:

1. **Smaller KV cache** (INT4, NVFP4, MXFP4): bandwidth reduction is bandwidth gained.
2. **GPU clock boost**: nominal boost 2,407 MHz, max 3,090 MHz. Sampled *during* benchmark load on this host: **2813-2932 MHz** (the `GPU during bench:` line every `verify-fast` run prints). This line read "~2,445 MHz under load" until #1671, which matched neither the spec nor any measurement in the tree.
3. **Batch > 1**: multiple sequences share weight loads, raising arithmetic intensity. Shipped for serving in v0.12.0 (PR #736): imp-server auto-sizes `max_batch_size` to free-VRAM headroom, so concurrent requests share a paged KV pool (continuous batching) instead of being serialized - Qwen3-Coder-30B NVFP4 cap 1 → 15, ~2.4× aggregate server throughput. `imp-cli` / `--bench` stay bs=1 (single-stream), so the perf baseline is unchanged.

## Open kernel work

Tracked in [`roadmap.md`](../roadmap.md). Highest-leverage items:

- Q4_K_M dense prefill gap vs llama.cpp: custom tiled MMQ kernel needed (dp4a shipped in PR #436 for small M; high-M gap remains).
- `cublasLtMatmulGrouped` with NVFP4 + device-side shapes: zero grouped algos returned on sm_120 as of cuBLAS 13.4. Re-probe on each toolkit release.
- MoE host-offload + CUDA Graphs (Phase 5.1): needs kernel-driven slot resolution via device-side lookup table. Deferred (2-4 weeks).
