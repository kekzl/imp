# sm_120 kernel notes

What was optimized for `sm_120a` (RTX 5090, GB202 Blackwell consumer), what did not move the needle, what is still open. Engineering reference, not a feature list.

Canonical clean-sheet spec of the optimal attention kernel (tiling, smem budget, MMA precision, lever-status table): [`KERNELS.md`](KERNELS.md).

## Hardware

| Spec | Value |
|---|---|
| Compute capability | `sm_120a` |
| SMs | 170 |
| Tensor cores | 680 (5th gen) |
| L1 / shared memory per SM | 128 KB (configurable split) |
| L2 cache | 96 MB (no L3 - that's only on data-centre Blackwell B200/B300) |
| Memory bandwidth | 1,792 GB/s (32 GB GDDR7, 512-bit) |
| FP4 dense / sparse | 3,354 / 6,708 TOPS |
| FP8 dense / sparse | 1,677 / 3,354 TFLOPS |
| FP16 dense / sparse | 838 / 1,677 TFLOPS |

`sm_120` uses register-based `mma.sync` only; what it lacks against datacenter Blackwell and why is [`ARCHITECTURE.md#target-architecture`](ARCHITECTURE.md#target-architecture). Native MMA shapes:

| Precision | Shape |
|---|---|
| FP16 | `m16n8k16` |
| FP8 | `m16n8k32` |
| FP4 (block-scaled) | `m16n8k64` |

The `f` family-feature suffix (`compute_120f`) enables FP8 MMA `kind::f8f6f4` and TMA warp-specialized grouped GEMM tactics. CMake < 3.31 does not understand the suffix; the build pins it via raw `--generate-code` (`CMakeLists.txt`) and disables `CMAKE_CUDA_ARCHITECTURES`.

| Topic | Detail |
|---|---|
| Two images shipped | `arch=compute_120a,code=sm_120a` (SASS); `arch=compute_120f,code=compute_120f` (**PTX**, not SASS - said `code=sm_120` until #1543) |
| Build options | `IMP_DISABLE_120F_FALLBACK` (default off) skips the PTX fallback for an RTX-5090-only fatbin; `IMP_DEVICE_LTO` (default off) links `code=lto_120a` IR per TU with SASS produced at the device link - measured neutral, hot kernels do not cross TU boundaries (`docs/audit/AUDIT_arch_2026.md` H-10) |
| GB203 (RTX 5080 / 5070 Ti) | runs the `compute_120f` PTX, JIT-compiled by the driver at load - not `sm_120a` SASS (`a` is architecture-specific, does not load on another chip); loses the TMA-WS grouped GEMM tactics, so the CUTLASS NVFP4 fast path is degraded; untested, no such card here (#1651) |
| SKU coverage | every consumer-Blackwell card is compute capability 12.0, so `sm_120a` SASS runs on the whole family incl. China-market GB202 (RTX 5090D, RTX 5090D v2); only the RTX 5090 (32 GB GDDR7, 1792 GB/s) is tested; 5090D keeps the full memory system, 5090D v2 cuts it to 24 GB on a 384-bit bus (~1344 GB/s, -25 %) - smaller usable model set (32 GB sizing assumptions in `docs/MODELS.md` don't transfer), roughly bandwidth-proportional decode (#1052) |
| cuBLASLt sm_120 block-scaled GEMM | 72 kernel names, byte-identical CUDA 13.3.1 (`libcublasLt.so.13.6.0.2`)/13.4.1 (`13.7.0.27`); MXFP8 `ue8m0xe4m3`/`ue8m0xe5m2` at one tile (`128x128x128_1x1x1`, matches `gemm_cutlass_mxfp8_sm120.cu:42`'s `Mx8ThreadBlockShape`); NVFP4 `ue4m3xe2m1` at `128x128x128` + `128x128x256`; datacenter Blackwell's cuBLASLt carries 4689 names against these 96; 13.4's `CUBLASLT_MATMUL_MATRIX_SCALE_VEC32_MN_K4_UE8M0` packs 4 UE8M0 exponents/uint32 in a plain MN-major layout (`round_up(M,4) x ceil(K/128)`), not CUTLASS' SfAtom - routing MXFP8 through cuBLASLt would need a second quantizer; `CUDA_R_8F_UE5M3` (13.4) is conversion-only, no `CUBLASLT_MATMUL_MATRIX_SCALE_*` mode or sm_120 kernel name uses it |

## What moved the needle

| Change | Path | Measured |
|---|---|---|
| FP8 attention prefill (`m16n8k32` QK^T) | `attention_fmha_sm120.cu` | +3.3% pp4096 |
| L2 persistence for KV | `set_l2_persist_kv` | measurable above 4K ctx |
| Aggressive split-K flash decode | `attention_paged.cu` | no regression at `tg256` |
| 16-byte `cp.async` for HD=256 | attention split-K | halves instruction count |
| Fused 3-way bias + sandwich-norm | various | -3 launches per layer |
| HD=256 FMHA at Bq=32 | `attention_fmha_sm120.cu` | enables sm_120 FMHA on Qwen3.5 |
| CUTLASS NVFP4 prefill cache for prequant SafeTensors (PR #88) | `executor_pre_dequant.cu` | Qwen3-Coder-30B NVFP4 decode 51 → 272 tok/s |
| NVFP4 prequant MoE decode fast-path (PR #85) | `cache_moe_native_nvfp4` | Qwen3.6 NVFP4 8.34 → 217 tok/s |
| MoE expert-offload auto-pick (PR #54) | `executor_moe.cu` | Qwen3-Coder-30B Q6_K 77 → 234 tok/s |
| VRAM-aware auto `max_batch_size` (server continuous batching, PR #736) | `engine_init_resolver.cpp` | Qwen3-Coder-30B NVFP4 server 258 → 609 tok/s @ conc16 (~2.4×) |

## Why batch=1 decode is memory-bound

Typical layer at 2048 tokens, 8 heads, 128 dim, FP16:

```
KV cache load   = 2048 × 8 × 128 × 2 B  = 4 MB
At 1.8 TB/s     → 2.2 µs per layer

Score compute   = 32 FLOPs/token × 2048 = 65 k FLOPs
At 838 TFLOPS   → 0.000078 µs per layer
```

Memory:compute ratio is ~28,000:1. Compute is free.

Both numbers were wrong until #1668: the quotient read `0.08 µs` (a factor of 1023 too large) and the ratio `~28:1` was derived from it; the conclusion does not change but the figures were unusable for sizing. 838 TFLOPS is also the **f16-accumulate** rate; FP32 accumulate, which `KERNELS.md:31` names as attention's largest compute loss, runs at 1/4 of it (253 TFLOPS measured, `tools/roofline/config.json:10`) - at that rate the compute side is 0.00026 µs and the ratio still ~8,600:1.

| No measurable decode win on this hardware | Why |
|---|---|
| FP8 decode scores | compute is already idle |
| Warp specialization | all warps already stream KV at peak bandwidth |
| TMA for paged KV | `cp.async` already at near-peak |
| Triple buffering | already double-buffered, marginal at best |

| What actually helps decode | Detail |
|---|---|
| Smaller KV cache (INT4, NVFP4, MXFP4) | bandwidth reduction is bandwidth gained |
| GPU clock boost | nominal boost 2,407 MHz, max 3,090 MHz; sampled *during* benchmark load on this host: **2813-2932 MHz** (`GPU during bench:` line every `verify-fast` run prints) - read "~2,445 MHz under load" until #1671, matching neither the spec nor any measurement in the tree |
| Batch > 1 | multiple sequences share weight loads, raising arithmetic intensity. Shipped v0.12.0 (PR #736): imp-server auto-sizes `max_batch_size` to free-VRAM headroom, concurrent requests share a paged KV pool (continuous batching) instead of serializing - Qwen3-Coder-30B NVFP4 cap 1 -> 15, ~2.4x aggregate server throughput. `imp-cli`/`--bench` stay bs=1 (single-stream), perf baseline unaffected |

## Open kernel work

Tracked in [`roadmap.md`](../roadmap.md). Highest-leverage items:

- Q4_K_M dense prefill gap vs llama.cpp: custom tiled MMQ kernel needed (dp4a shipped in PR #436 for small M; high-M gap remains).
- `cublasLtMatmulGrouped` with NVFP4 + device-side shapes: zero grouped algos returned on sm_120 as of cuBLAS 13.4. Re-probe on each toolkit release.
- MoE host-offload + CUDA Graphs (Phase 5.1): needs kernel-driven slot resolution via device-side lookup table. Deferred (2-4 weeks).
