# File-Size Audit

Append-only log of file-size audits for imp. Each run is a dated section; the gate
that enforces these thresholds is `tools/check_filesize.py` (config:
`tools/filesize_thresholds.toml`). See also AGENTS.md / CLAUDE.md
"File Layout & Size".

---

## 2026-06-24 — baseline audit

### Why size, and which size

A file's size matters here for **recompile blast radius**, not readability. Every
`.cu` is one translation unit: editing a single kernel in a 1.5k-LOC `.cu` forces
nvcc to re-`ptxas` the whole TU (the slowest stage of an sm_120a build) with no
intra-file parallelism. Headers fan the cost out further — a fat `.cuh` re-triggers
every TU that includes it. Line count is only a **proxy** for that cost; the
thresholds below are smells, not hard rules.

**Metric.** Two columns are reported per file:

- **code** — non-blank lines after stripping C/C++ comments with a char state
  machine that does *not* treat `//` or `/*` inside string/char literals as comment
  starts (honest in both directions).
- **raw** — total physical lines (`wc -l`, verified equal).

Thresholds apply to **code LOC** so that heavily doc-commented files are not
penalized. RAW is shown alongside for transparency (anti-cheat: the stripper is the
same one the gate uses, reported in both columns — no frigging the counter).

### Classification

Files are bucketed by extension + path, matching the gate:

- **header** — `.cuh` / `.hpp` / `.h` (any path).
- **kernel** — `.cu` under `src/compute/`, `src/quant/`, `src/exec/` (the
  compute / quant / graph hot-path).
- **tu** — every other `.cu` (runtime, api, model, memory, vision, tests) and all
  `.cpp`.

Coverage: **494 files** across `src/`, `tools/`, `tests/` (180 header · 102 kernel
· 212 tu) — 100% of the three roots.

### Thresholds (code LOC) and rationale

| group  | warn | hard-review | rationale |
|--------|-----:|------------:|-----------|
| kernel |  500 |         600 | strictest: a kernel TU's `ptxas` pass dominates incremental builds |
| tu     |  600 |         800 | host code compiles fast; loaders/schedulers/test suites legitimately large |
| header |  500 |         700 | a change fans out to every includer; p90 is only ~113 code LOC, so >500 is already a strong outlier |

These are derived from the actual distribution below, **not** reverse-fit to make
the baseline trivially green: the real over-hard-review counts are **19 kernel /
17 tu / 1 header = 37**, every one of them listed in the gate's `[allow]` with a
reason.

### Why-large classification (over-threshold files)

Each flagged file was inspected (not guessed) and assigned one cause:

- **(a)** multiple independent kernels/concepts bundled in one TU → *split candidate*
- **(b)** explicit template instantiations / specializations inline
- **(c)** legitimately monolithic (one cohesive unit, or one test target whose cases
  all exercise the same unit) → kept as-is

Over-hard-review breakdown: **(a) 12 · (b) 1 · (c) 24**. The 12 `(a)` files are the
genuine split candidates (notably `tools/imp-server/handlers.cpp` at 3625 code LOC,
the per-kernel `compute/*.cu` god-files, and `model/{gguf_loader,chat_template}.cpp`).
The 24 `(c)` files are cohesive (the Jinja engine, the tokenizer, single
kernel-families, per-unit test targets) and are not worth splitting for splitting's
sake. The one `(b)` file is the dp4a GEMV trait library — already a *consolidation*
of ~33 hand-written kernels into templates, but a header, so its include
blast-radius is the reason it tops the header list.

## 2026-06-24 — remediation: split all 12 `(a)` candidates

All 12 files classified `(a)` (bundling independent concepts) in the baseline audit
above were split into smaller TUs. **Move-verbatim only** — every relocated hunk is
byte-identical to the original (no kernel/host-body rewrite, no numeric change); the
sole edits beyond cut-and-paste are linkage adjustments required for cross-TU use
(e.g. `static`→external, a moved `thread_local` definition, forward `__global__`
declarations for PDL-registered kernels). Shared device helpers / `__constant__` /
anon-namespace symbols were lifted into per-file internal headers
(`*_internal.cuh` / `*_internal.h`). The 25 `(c)`/`(b)` files stay in `[allow]` —
not worth splitting.

**Verification:** full Docker build (CUDA 13.3) compiles + **device-links** all 359
targets (exit 0) — proves no duplicate/missing-symbol or ODR fault. CPU test suites
green: `test-text` 190/191 (chat-template/jinja/tokenizer host splits), `test-core`
331/333, `imp-tests-unit` 37/37 (skips are model-gated). **GPU numeric verification
(degeneration + perf gate) is required before merge** and runs once the card is free.

## 2026-07-30 — a note on `src/runtime/engine.cpp`, which sits ON the limit

Not an audit run; one fact worth writing down because it has now cost two
sessions a red CI job (#1124, #1125, and again in #1127).

`src/runtime/engine.cpp` measures **exactly 800 code LOC**, which is the `tu`
group's **hard** threshold. The gate fails at 801, so *any* single added line —
including wrapping one function call across an extra line — turns the blocking
`File size` job red without touching anything a reviewer would call growth.

Practical consequences, in order of preference:

1. If you touch `engine.cpp` at all, run `python3 tools/check_filesize.py`
   **before** committing. It reports in under a second.
2. Prefer edits that are line-neutral or negative. Both times so far the fix was
   trivial once seen: fold a call's arguments onto fewer lines, or collapse an
   intermediate `const size_t want = …; const size_t cap = std::max(…, want);`
   into one expression.
3. It is *not* on the `[allow]` list and should not be added to it to buy room —
   it is on the limit because it accreted engine-init responsibilities, and the
   right remediation when it next needs to grow is to move one of them out
   (the arena/slot-pool opening block and the shadow-plan logging are the two
   obvious candidates, both already self-contained).
