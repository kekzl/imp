## Lever 3 shipped: weight-streaming dense NVFP4 GEMM at decode rows (2026-11-02)

Root cause of the M 16 gap: v2 (`nvfp4_gemm_smallm_v2.cu`, 64-row CTAs, 92 KiB smem ring, 1 CTA per SM) splits K into
`ceil(160 / n_tiles)` stripes plus a reduce launch whenever N < 5120, and refuses K % 256 != 0. On Gemma-4 that is o
(4 stripes), gate and up (5 stripes each, no sibling launch: 66 tiles < 80), and down 2816 x 2112 on the 128-row prompt
tile kernel; each call paid 8-13 us against a 2-7 us weight floor.

`src/quant/nvfp4_gemm_smallm_ws.cu` (`gemm.nvfp4_smallm_impl` 3, default):

| Item | Setting |
|---|---|
| CTA | 32 weight rows (16 when N % 32) x the whole K, 8 warps; warp w owns 128-element k-steps ks % 8 == w |
| Operands | W = MMA A (rows), Xq = B (8 tokens per n-tile, 1 / 2 / 4 tiles by M); LDG.128 per lane + 3-shuffle quad transpose into m16n8k64 fragments, no smem ring |
| Reduce | warp partials summed in warp order in smem, ts and beta in fp32, one launch, K % 64 (a K % 128 == 64 tail step runs one MMA) |
| Policy | `src/exec/smallm_policy.h`: ws where v2 splits K 4+ ways, cannot fuse siblings in one stripe, or refuses K % 256; v2 elsewhere |
| Gemma-4 | dense MLP (shared-expert path) gate\|up as one sibling launch, K=V global layers q\|k as one launch |
| Numerics | a row's bits depend on K only (not M, position, CTA config); siblings bit-equal to singles; double reference M 1..32 |
