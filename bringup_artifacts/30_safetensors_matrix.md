## FP8 sourcing strategy

Because **no local SafeTensors checkpoint ships FP8 weights** (every
F8_E4M3 tensor in the local NVFP4 inventory is a per-block scale, not a
weight payload), the bring-up exercises the FP8 path the same way main
already runs it: **runtime FP8 quantization on FP16/BF16 reference
weights**, gated by:

```
[kv_cache] dtype = "fp8"           # → QType::FP8_E4M3, runtime/config.h:36
[attention] fp8_prefill = "auto"   # default ON, runtime/config.h:42
[attention] fp8_fmha    = "auto"   # default ON, runtime/config.h:43
```

Code citation:

- Auto-promotion of FP16 → FP8 KV remains only as the `fp8_auto_legacy`
  opt-in (`src/runtime/engine.cpp:382-388`). Default is FP16 KV unless
  the user sets `kv_cache.dtype=fp8` explicitly.
- FP8 FMHA prefill dispatch:
  `src/compute/attention_dispatch.cu:60` —
  `const bool use_fp8_fmha = RuntimeConfig::current().attention.fp8_fmha != "never";`
  followed by `fmha_sm120_fp8_prefill(...)`.
- Deterministic-cuBLAS auto-pin when FP8 KV is active:
  `src/runtime/engine.cpp:405-416`.
- Loader `F8_E4M3` recognition (kept dormant for current inventory):
  `src/model/safetensors_loader.cpp:237`.

**Decision:** for Phase-3 FP8 column cells, do NOT upconvert NVFP4
weights to FP8. Instead:

1. Use a **dense FP16/BF16 SafeTensors reference** when one is available
   (none is local — would have to be downloaded out-of-band; not in
   scope for this read-only inventory).
2. Or, use the existing **GGUF Q6_K/Q8_0 baselines** with the runtime
   FP8 toggles. That is what the existing `verify-fast` gate and the
   FP8 KV regression suite do today, and it is the only FP8-on-disk
   surface imp actually exercises in CI.

The matrix's `FP8` column therefore stays `NO_WEIGHTS` (or `UNSUPPORTED`
for GDN/Gemma-4 KV) for SafeTensors specifically — there is no
SafeTensors FP8 weight artifact to bring up.
