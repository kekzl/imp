## What is imp

A C++20/CUDA inference engine that targets exactly one chip family: NVIDIA Blackwell (`sm_120`). No portability layer, no FP16 dequant fallback in the hot path, no wrapper around llama.cpp or vLLM. imp ships its own GGUF and SafeTensors loaders, BPE tokenizer, paged KV cache, attention kernels, MoE routing, Gated DeltaNet + Mamba2 scans, CUDA Graphs, and an OpenAI/Anthropic-compatible HTTP server — ~93k LOC of C++/CUDA, every line generated by an AI coding agent.

## Why this exists

The RTX 5090 shipped with native FP4 tensor cores, 32 GB GDDR7 at 1.8 TB/s, and a new ISA (`sm_120`) that no existing inference engine fully exploits. llama.cpp targets broad hardware compatibility and runs GGUF through dequant-to-FP16 paths — fast everywhere, but leaving Blackwell-specific features (NVFP4 block-scaled MMA, FP8 `kind::f8f6f4`, TMA warp-specialized grouped GEMM) on the table. vLLM targets datacenter Blackwell (B200/B300, `sm_100`) and gates key backends like FlashInfer MoE on `tcgen05` — an opcode family that consumer Blackwell doesn't have.

That leaves a gap: 30B-class MoE models (Qwen3-Coder, Qwen3.6, Gemma-4) fit in 32 GB as NVFP4 prequant and should decode at 150–270 tok/s on this hardware, but neither engine delivers that today. imp exists to close that gap — a single-target engine that treats the RTX 5090 as the only GPU that matters and optimizes accordingly.

NVFP4 prequant (from [NVIDIA Model Optimizer](https://github.com/NVIDIA/Model-Optimizer)) is the native weight format for Blackwell's FP4 tensor cores. imp loads these SafeTensors directly into its NVFP4 decode cache and CUTLASS GEMM kernels with no re-quantization. For GGUF models, imp uses an NVFP4 decode cache that converts Q8_0/Q6_K weights to FP4 at init time, getting the bandwidth benefit of sub-byte weights on the decode hot path while keeping full-precision prefill.

## Should I use this?

**Use [llama.cpp](https://github.com/ggerganov/llama.cpp) if** you want a stable, mature engine with broad model/hardware support and CPU fallback. It runs everywhere and supports everything.

**Use [vLLM](https://github.com/vllm-project/vllm) if** you serve high-concurrency batched workloads on datacenter GPUs (H100/B200). It has continuous batching, PagedAttention at scale, and production-grade serving.

**Use imp if** you have Blackwell consumer/workstation hardware (RTX 5090, RTX PRO 6000), want native NVFP4/FP4 without dequant overhead, and don't mind running a prototype. imp is fastest-on-Blackwell for single-user decode, but it's experimental, single-GPU, and single-author.

## Known limitations

- **Single GPU only.** No tensor parallelism, no multi-GPU.
- **Blackwell only.** No Hopper, Ada, Ampere. No AMD, Intel, Apple, or CPU paths.
- **Q4_K_M prefill is slow.** -48–59% vs llama.cpp. Known issue, needs a custom IMMA kernel.
- **Only tested models work reliably.** Anything not on the [supported list](docs/supported-models.md) may load but hasn't been verified.
- **Prefill numbers are noisy.** cuBLAS autotuning causes up to 2.6x variance across container restarts.
- **Single-author, experimental.** Don't deploy this anywhere it matters.

## Quickstart

Everything runs in Docker — no local CUDA toolkit needed.

```bash
git clone https://github.com/kekzl/imp.git && cd imp

# Drop a GGUF or SafeTensors model into ./models/
mkdir -p models

# Build and run the server
docker compose build imp-server
docker run --gpus all -v ./models:/models -p 8080:8080 \
  imp:latest --model /models/your-model.gguf

# Hit the OpenAI-compatible endpoint
curl -s http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"messages":[{"role":"user","content":"Hello!"}],"max_tokens":64}'
```

CLI reference, server flags, config, and C API: [`docs/usage.md`](docs/usage.md).

## Features

| | |
|---|---|
| **Quantization** | GGUF Q4_K_M/Q5_K_M/Q6_K/Q8_0, SafeTensors NVFP4 (prequant), MXFP4. NVFP4 KV cache (`--kv-nvfp4`) for 3.9x context compression at decode parity. |
| **Attention** | cuBLAS short-seq, FP8 FMHA (CUTLASS), paged KV cache (block_size=16). Auto-dispatch per layer/dtype/seqlen. |
| **Architectures** | Dense transformers, Mixture-of-Experts (grouped GEMM), Gated DeltaNet (fused recurrent scan), Mamba2 (SSM), SigLIP vision encoder. |
| **Blackwell kernels** | NVFP4 block-scaled MMA, FP8 MMA, TMA warp-specialized grouped GEMM, PDL, Green Contexts, packed `cvt.e4m3x2`. |
| **Server** | OpenAI (`/v1/chat/completions`) + Anthropic (`/v1/messages`), streaming, prefix caching, JSON-schema constraining, tool calling. |
| **Runtime** | CUDA Graphs (auto per model), `imp.conf` + CLI config, Jinja2 chat templates with macro support. |

## How was this built?

imp is written entirely by [Claude Code](https://claude.ai/claude-code) (Opus 4.6 → 4.7) — 848 commits, ~93k lines of C++/CUDA, 96 test files with 692 tests. A human ([@kekzl](https://github.com/kekzl)) directs architecture decisions, picks models, and runs benchmarks. The AI agent writes all code: GGUF parser, BPE tokenizer, paged KV cache, CUTLASS GEMM dispatch, NVFP4/FP8 attention kernels, MoE routing, GDN scan kernels, HTTP server, CI, the build system — nothing is copy-pasted from other engines.

This is a running experiment in how far AI-generated systems code scales. The [architecture doc](docs/architecture.md) covers the end-to-end pipeline if you want to see how the pieces fit together.

## Building from source

```bash
# With CUDA 13.2+ on the host:
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j$(nproc)

# Or via Docker (canonical):
make build          # → imp:test image
make verify-fast    # build + tests + perf gate (~90s)
```
